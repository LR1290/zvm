# R46.93 — Blacklist de IPs: confirmação no banco e proteção contra auto-bloqueio

**Data:** 12/11/2026  
**Escopo:** Backend Admin (Render), código frontend de Segurança, regressões simuladas. Nenhuma licença/cliente foi alterado diretamente.

## Achado forense

A lista de IPs bloqueados era alterada primeiro em memória por `addIpBlacklistEntry` / `removeIpBlacklistEntry`, e só depois se tentava persisti-la por `saveIpBlacklist`. Essa função absorvia exceções: em caso de indisponibilidade do MongoDB, os endpoints respondiam `ok:true` mesmo se a gravação tivesse falhado. Além disso, `$set` da lista inteira poderia sobrescrever atualização concorrente. Havia risco de o próprio administrador bloquear seu IP e perder acesso ao painel.

## Correção consolidada

- **Leitura pela fonte de verdade:** GET de blacklist usa `settings.main.ipBlacklist` no MongoDB; erro retorna HTTP 503, não divulga lista antiga como atual.
- **Escrita atômica:** inclusão por `$addToSet`, remoção por `$pull`; não substitui a lista completa. Valores IPv4-mapped legados são reconhecidos na remoção.
- **Confirmação antes do sucesso:** após update, nova leitura confirma presença/ausência. Só então a memória de bloqueios é sincronizada e o endpoint devolve `ok:true`. Falha de escrita ou leitura mantém status inconclusivo, não representa sucesso.
- **Evitar auto-bloqueio:** inclusão do próprio IP da sessão administrativa retorna HTTP 409 com `self_ip_block_forbidden`.
- **Limite operacional:** 5.000 IPs canônicos; entrada inválida é rejeitada.
- **Frontend:** mensagem específica para falha MongoDB/auto-bloqueio, bloqueio de POSTs concorrentes, atualização GET de reconciliação, sem repetição automática de operação com resultado incerto.
- **Código residual:** removidas funções antigas sem referências. O asset anterior foi preservado **somente** porque páginas já abertas podem solicitá-lo pelo caminho imutável; a página Admin nova usa um hash diferente.

## Pendências arquiteturais fora desta revisão

A memória de blacklist ainda é carregada por processo para filtrar requisições rapidamente. O novo fluxo sincroniza na leitura e nas alterações administrativas, mas replicação instantânea entre múltiplas instâncias exigiria mecanismo dedicado de invalidação/pubsub; no plano Starter atual, a ZVM opera com apenas uma instância. Não introduzir polling a cada requisição.

A remoção de logs do Admin utiliza rotina de persistência que absorve falhas; merece revisão com fila serializada/controle de geração antes de mexer, para evitar perda de eventos enquanto a limpeza acontece.
