# ZVM — Gate de admissao da RELEASE (R46.89)

## Por que isto existe

Em 17/10/2026, o servidor em producao reconhecia 16 identidades V2 mas a RELEASE 0.9.49 distribuida possuia buildId ainda nao registrado. A autoridade rejeitava a RELEASE com BUILD_ID_NOT_ALLOWED (HTTP 403). O hotfix registrou **somente** a identidade exata da 0.9.49; o servidor foi reimplantado manualmente porque o servico oficial usa autoDeploy=off. DEV e RELEASE seguem autoridades distintas.

## Etapas obrigatorias ANTES de publicar na Chrome Web Store

1. Gerar o ZIP final da RELEASE, verificar sua integridade, congelar seu SHA-256. Nao modificar nem recriar o pacote a partir deste ponto.
2. Cadastrar a identidade EXATA de app/security/build-identity.json + app/security/integrity.json em zvm-build-registry-v2.json via PR revisado. Nunca cadastrar automaticamente um arquivo desconhecido ou revogado.
3. Rodar `npm run gate:release -- --artifact /caminho/RELEASE.zip`. **GATE_BLOCKED significa NAO PUBLICAR.** O comando recusa divergencia de versao, perfil, canal, hash da origem, fingerprint ou ID oficial CWS. ZIP exige `unzip` no PATH (Ubuntu/macOS/GitHub runner); no Windows, pode-se apontar para uma pasta extraida.
4. Apos merge, **implantar a mesma revisao no Render**. Como autoDeploy esta desligado, merge por si so nao ativa o registro. Exigir estado `live` da revisao correta; conferir nos logs o contador `Registry V2 active` e ausencia de erros.
5. Usar uma licenca dedicada a QA para autenticar e renovar a sessao **na RELEASE exata**. Testar extensao atualizada sem apagar armazenamento, isolacao entre contas e retorno de 403 nos endpoints V4. Se houver BUILD_ID_NOT_ALLOWED, BUILD_NOT_ALLOWED ou EXTENSION_ID_NOT_ALLOWED, **NAO PUBLICAR**.
6. Somente apos as cinco etapas, enviar o ZIP cujo SHA-256 foi congelado. Registrar SHA-256, buildId, fingerprint, commit, deployId e prova do teste. Se o ZIP for regerado, reiniciar a sequencia.
7. Verificar os 403 e falhas de login nas horas seguintes e ter a RELEASE anterior pronta para reversao.

## Como automatizar ainda mais

Este CLI e um gate **offline**, nao uma prova de que o servidor Render ativo ja recebeu a autorizacao. Antes de garantir bloqueio real contra publicacao por engano, integrar o gate a um workflow unico que faca o upload para a CWS somente quando todos os checks tiverem passado. Configurar no GitHub a verificacao de CI como `required status check` e bloquear upload manual fora desse processo. Enquanto esse workflow ainda nao existir, a etapa continua obrigatoria operacionalmente.

## Garantias e limites

- Nao altera cadastro de clientes, chaves, licencas ou banco de dados.
- Nao desliga ZVM_BUILD_ENFORCE, nem libera builds por faixa de versao.
- Nao usa ZVM_CWS_COMPAT para admitir um fingerprint diferente.
- Nao marca a publicacao como liberada ate a checagem live e o teste da RELEASE por uma licenca de QA.
